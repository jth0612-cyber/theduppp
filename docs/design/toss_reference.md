# 토스 디자인 글 참조 정리 (2026-11-25)

출처: toss.tech 디자인 카테고리 1~30페이지 전부, 토스피드 디자인 검색 결과.
색·아이콘·글꼴·그림·캐릭터는 가져오지 않는다. 화면 구성, 흐름, 움직임, 문구, 접근성 원칙만 쓴다.
수치는 토스 자체 서비스의 보고치이므로 우리 제품의 목표치로 옮기지 않는다.

## 1. 화면 구성

- 한 화면에 한 가지 일. 화면 리뷰 때 묻는다: 1초 안에 이해되나, 주요 버튼이 하나인가, 질문에 3초 안에 답할 수 있나, 기다림이 없나.
- 화면은 사업·조직 단위가 아니라 사용자 행동 단위로 나눈다(예: 질문하기, 확인하기, 받기).
- 같은 목적의 버튼은 모든 화면에서 같은 자리, 같은 동작. 컴포넌트가 아니라 화면 패턴(목록 화면, 단계 작업 화면, 옆 정보 영역)으로 맞춘다.
- 판단에 필요한 핵심 숫자를 가장 크게, 세부 정보는 작게. 재미 요소가 있는 화면도 가장 위·가장 큰 숫자는 사용자 자신의 기록.
- 추천·홍보는 사용자 자료와 같은 자리에서 다투지 않게 다른 층에 둔다. 큰 그림·강한 색을 빼고 글과 버튼 위계로.
- 추천은 여럿보다 가장 좋은 것 하나. 선택지가 많으면 오래 고민한다.
- 쓰임이 적은 기능은 과감히 뺀다. 빼도 사용자가 알아채지 못하는 경우가 많다.
- "더보기"를 넣으면 깊이와 노출 순서 규칙이 생긴다. 규칙을 늘리지 않는 쪽(Less Policy)을 먼저 찾는다.
- 숨은 제스처(당겨 내리기 등)는 거의 쓰이지 않는다. 눈에 보이는 탭·버튼으로.
- 아래에 내용이 더 있으면 스크롤할 수 있다는 신호를 준다(끝부분 흐림 등). 여러 기기 높이에서 확인.
- PC 화면은 모바일 화면을 늘려 붙이지 않는다. 큰 화면에서 쓰는 방식이 따로 있다.
- 메뉴 구조는 사용자가 묶는 방식(카드 소팅)으로 확인한다. 상하위 이름이 겹쳐 보이면 헷갈린다.

## 2. 입력과 흐름

- 하나만 고르는 화면은 확인 버튼 없이 고르면 바로 다음으로.
- 자릿수가 정해진 입력(전화번호, 인증번호)은 다 채우면 자동으로 다음 단계.
- 입력 종류에 맞는 키보드(숫자 칸은 숫자 자판), 화면에 들어오면 첫 칸에 바로 커서.
- 시스템이 이미 아는 정보는 미리 채운다. 묻는 질문은 3~4개를 넘기지 않는다. 5초 안에 답하기 어려운 질문, 민감한 질문은 부담이 크다.
- 어려운 선택 질문은 쉬운 사실 질문으로 바꾼다("어떻게 할래요?" 대신 "서류 있나요?"). 예시 그림을 같이 보여 준다.
- 입력이 맞는지 바로 확인시킨다(번호를 넣으면 이름을 바로 보여 줌). 형식이 까다로운 입력은 검색해서 고르기로.
- 목록에서 고르게 할 때는 전부가 아니라 그 사용자에게 해당하는 것만 보여 준다.
- 행동을 요청하기 전에 얻을 것을 구체적인 숫자로 먼저 보여 준다(Value first, cost later).
- 진행 상태는 내부 단계를 다 보여 주지 않고 사용자 말로 3단계 안팎.
- 기다리는 화면에는 무엇을 하고 있는지, 언제 끝나는지를 보여 준다. 의미 없는 로딩 그림만 돌리지 않는다.
- 끝 화면은 다음 행동의 시작점으로 설계한다.
- 일부러 어렵게 만드는 단계(삭제 확인 등)는 누구에게나 같은 난이도. 실패를 겁주는 연출은 넣지 않는다.
- 왜 이 정보가 필요한지 입력 화면 위에 짧게 밝히면 끝까지 가는 비율이 오른다.

## 3. 움직임

- 눌렀을 때 회색 바탕만 바꾸지 말고 살짝 더 눌리는 짧은 움직임을 같이 준다.
- 빠르게 시작해 부드럽게 멈추고 끝에 약한 반동. 크게 튀는 움직임은 정보를 볼 때 산만하다.
- 요소를 한꺼번에 띄우지 말고 시간차를 둔다(바탕 → 카드 → 내용 → 아래 버튼).
- 움직임 곡선은 이름 붙인 토큰으로 관리하고 종류를 줄인다. 한 대상에는 움직임 하나.
- 탭하는 순간 숫자가 바로 올라가는 등 결과를 즉시 보여 준다.
- 화려한 움직임보다 간결한 쪽이 이해가 빠르다(현장 테스트 결과).

## 4. 문구 (토스 8가지 라이팅 원칙과 에러 메시지 원칙)

- 버튼을 누르면 다음에 무슨 일이 일어날지 미리 알 수 있게 쓴다.
- 빼도 뜻이 같은 단어, 빈자리를 채우려고 넣은 문장은 뺀다. 사용자가 이미 아는 것은 생략한다.
- 겁주거나 강요하는 말("놓치면 손해") 대신 중립적인 권유.
- 소리 내어 읽어 자연스러운지, 특정 집단만 아는 말은 아닌지 확인한다.
- 질문형 버튼("어떤 서류가 필요한가요?")보다 행동형("필요한 서류 확인하기").
- 안내·배너 문구는 지금 할 행동 하나만. 조건은 숫자로(예: 3문항 남음).
- 에러는 먼저 안 생기게 막는다. 생기면 상황, 이유, 해결 방법을 쓰고 해결 버튼을 붙인다. 설명이 길면 사라지는 토스트 대신 창으로.
- 개발 용어 대신 사용자 말. "안 돼요, 없어요" 대신 할 수 있는 행동 중심으로.
- 반복되는 에러·안내 문구는 템플릿으로 만들어 같은 상황에 같은 문구.
- 입력칸의 용도가 헷갈리면 칸 아래에 짧게 밝힌다(예: 나만 볼 수 있는 메모).

## 5. 접근성과 다크 모드

- 장애인 전용 화면을 따로 만들지 않고 기본 화면 하나로 모두가 쓰게 한다.
- 버튼은 버튼처럼 보이게. 글자나 화살표(>)만으로는 누를 수 있다는 신호가 약하다(특히 시니어).
- 화면 읽기 도구용 이름에는 내용, 역할(버튼·스위치), 상태(켜짐·꺼짐)를 빠짐없이. 장식 아이콘은 읽히지 않게.
- 창·시트가 열리면 초점을 그 안으로 옮기고, 닫는 방법을 둔다.
- 큰 글자 설정에서 화면이 깨지지 않는지 확인한다. 큰 글자에서는 아이콘도 함께 키운다.
- 작은 라디오 원은 누르기 어렵다. 글자를 포함한 줄 전체를 누를 수 있게. 여러 개 고를 수 있는지는 문구로 밝힌다.
- 예시 그림은 예시라는 표시를 분명히, 실제 개인 정보처럼 보이는 글은 넣지 않는다.
- 색은 사람이 느끼는 밝기가 고른 색 공간(OKLCH)에서 단계를 맞춘다. 주요 색 조합은 대비 기준을 넘게 설계한다.
- 다크 모드는 라이트를 뒤집지 않고 따로 밝기 기준을 세운다(다크에서 대비를 더 강하게). 다크 팔레트를 1:1로 짝지어 자동 대응.
- 아이콘은 흰 바탕과 검은 바탕 모두에서 보이게. 회색(비활성처럼 보이는) 아이콘은 대상을 알아보기 어렵다.

## 6. 만드는 방식

- 꼭 있어야 하는 기능부터 만들고 검증한다.
- 정지 시안보다 실제 기기에서 움직여 보며 고친다. 공통 패턴을 먼저 정하면 새 화면은 패턴을 골라 조합한다.
- 공통 규칙에 맞지 않는 예외는 억지로 끼우지 않고 따로 둔다. 결정 이유를 문서에 남긴다.
- 출시 후에도 실제 사용자 5명 안팎으로 짧게 자주 테스트한다. "쓸 것 같나요?" 대신 실제 행동을 묻는다.
- 개편 직후 반응보다 한 달 뒤 반응을 본다.
- 클릭률만 보지 말고 클릭 뒤 끝까지 간 비율을 같이 본다. 한 번에 가설 하나만 바꿔 실험한다.

## 우리 제품에 이미 반영한 것 (2026-11-25)

- 아래에서 올라오는 확인 시트, 삭제는 빨간 확인 버튼, 열리면 초점 이동, Esc·바깥 누르면 닫힘.
- 누름 반응(scale .97), 끝에 약한 반동이 있는 시트 움직임, 화면이 열릴 때 내용이 6px 떠오름, 큰 숫자 올라가기.
- 휴대폰 폼의 주요 버튼은 맨 아래 가로 전체.
- 회차 고르기는 확인 버튼 없이 고르면 바로 이동(`data-autosubmit`), 로그인은 첫 칸에 커서, 숫자 칸은 숫자 자판.
- 저장·오류 알림 토스트(오류는 더 오래), 이동 중 위쪽 줄, 그림 자리 회색 반짝임.
- 다크 모드 색을 따로 정하고 모든 조합 대비 4.5 이상. 아이콘은 화면 읽기 도구가 읽지 않음(aria-hidden).
- 시험 분석 화면 정리(한 화면 한 가지 일, 총평·해설 영상 접기).
